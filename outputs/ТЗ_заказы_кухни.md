# Техническое задание: веб-приложение для заказов кухни

**Версия:** 1.0, подготовлена по исходной Excel-книге от 17.11.2026  
**Назначение:** быстрый сбор заявок кухни и формирование понятного списка закупки для провизора.

## 1. Цель и границы первой версии

Создать адаптивное веб-приложение, в котором шеф-повар управляет пользователями и справочниками, сушефы формируют заявки по каталогу продуктов, а провизор получает сгруппированный по поставщикам список закупки и отмечает обработку позиций.

Первая версия использует React для клиентской части, FastAPI для API и PostgreSQL для хранения данных. Приложение поставляется в Docker Compose, чтобы его можно было запустить локально для проверки и развернуть на сервере.

Внешняя отправка заказов поставщикам, складской учёт, автоматическое списание остатков, интеграции с бухгалтерией и мобильные приложения в эту версию не входят.

## 2. Роли и права

| Роль | Возможности |
|---|---|
| Шеф-повар / администратор | Просматривать все заявки; создавать, редактировать, отключать аккаунты сушефов и провизоров; управлять каталогом, категориями и поставщиками; привязывать товар к поставщику; видеть историю и статусы заявок. |
| Сушеф | Просматривать доступный каталог по категориям и поиску; собирать заявку; указывать количество и комментарий; сохранять черновик и отправлять заявку; просматривать собственные заявки и их статусы. |
| Провизор | Просматривать отправленные заявки, сводный список позиций, сгруппированный по поставщикам; отмечать позиции как заказанные/полученные или требующие уточнения; оставлять комментарии; экспортировать список для работы. |

Доступ к функциям определяется ролью на сервере. Неактивный аккаунт не может войти. Пользователи не создают аккаунты самостоятельно: их заводит шеф-повар.

## 3. Основные сценарии

### 3.1 Сушеф оформляет заявку

1. Входит в приложение и открывает каталог.
2. Выбирает категорию либо вводит название продукта в поиск.
3. Указывает количество в единице измерения товара. Для нескольких товаров вводит данные прямо в списке, без отдельной карточки каждого товара.
4. При необходимости добавляет комментарий к позиции.
5. Проверяет краткую сводку заявки и отправляет её.
6. Получает подтверждение с номером и временем отправки; после отправки видит статус заявки.

Пустые количества не попадают в заявку. Количество должно быть больше нуля. Отправленная заявка сохраняет автора и значения на момент отправки.

### 3.2 Провизор обрабатывает закупку

1. Открывает список новых заявок либо сводку за выбранную дату/период.
2. Видит товары, сгруппированные по поставщику, с категориями, количеством, единицами, комментарием и автором заявки.
3. Отмечает позицию статусом: «К заказу», «Заказано», «Получено», «Нужно уточнить».
4. Может отфильтровать список по поставщику, статусу и дате.
5. При необходимости экспортирует текущую сводку в XLSX или CSV для передачи/печати.

Заявка сушефа и список закупки связаны: изменения статусов доступны провизору, а шеф-повар видит ход обработки.

### 3.3 Шеф управляет приложением

Шеф создаёт аккаунты и задаёт имя, логин, временный пароль и роль. Предусмотреть смену пароля пользователем после первого входа и принудительный сброс пароля шефом. Шеф редактирует справочник товаров, категории и поставщиков, включая привязку товара к одному или нескольким поставщикам, если это подтверждено бизнес-правилом.

## 4. Экраны и интерфейс

1. **Вход:** логин и пароль, сообщение об ошибке без раскрытия существования учётной записи.
2. **Каталог сушефа:** поиск сверху, категории, список/строки товаров, поле количества, быстрый комментарий, индикатор позиций в заявке и кнопка отправки. Добавление товара и количества должно требовать минимум действий.
3. **Проверка и отправка:** компактный список выбранного, возможность вернуться и поправить количество, подтверждение отправки.
4. **Мои заявки:** дата, статус, количество позиций, просмотр состава.
5. **Рабочее место провизора:** заявки/сводка, фильтры, группировка по поставщику, статусы и экспорт.
6. **Панель шефа:** пользователи, товары, категории, поставщики, непривязанные товары, все заявки и история.

Интерфейс минималистичный, русскоязычный, с ясными названиями кнопок, заметными статусами и без перегруженных таблиц. На телефоне каталог и ввод количества должны быть удобны одной рукой; широкие сводные таблицы превращаются в карточки или горизонтально прокручиваемые строки. На планшете и компьютере используются более плотные таблицы. Все основные действия доступны с клавиатуры; поля имеют подписи, ошибки объясняют, что исправить.

## 5. Данные и импорт исходной книги

В загруженной книге обнаружены листы:

- **«Терминал су-шефа»** — рабочий экран заявки: раздел, номенклатура, количество, комментарий; диапазон содержит около 207 строк с наименованиями, но встречаются строки, похожие на пояснения/служебные заголовки.
- **«Продукты»** — каталог с полями: №, раздел, поставщик, номенклатура, минимальный остаток, статус привязки. В книге 197 записей: 185 имеют статус «Привязан», 12 — «Требует привязки».
- **«Поставщики»** — 39 строк названий поставщиков и количества позиций. Есть варианты написания и регистра, например «Глобал Фуд»/«глобал Фуд», «Метро»/«метро», несколько вариантов «Элит Трейд»; есть составные значения с несколькими продавцами через `/`.
- **«Без поставщика»** — 113 строк номенклатуры, 22 значения минимального остатка указаны как `???`.
- **«Заказы поставщикам»** — представление закупки с полями поставщик, раздел, номенклатура, количество, комментарий; пояснение листа указывает на тестовые количества. Эти числа нельзя импортировать как реальные заявки.

### 5.1 Правила импорта

- При первом импорте загрузить справочник товаров и категории из листа «Продукты»; если в нём нет названия или категории, использовать данные терминала только как источник сопоставления после ручной проверки.
- Загружать поставщиков как справочные записи, сохраняя исходное написание в поле «исходное имя». Предлагать объединение похожих названий, но не склеивать автоматически: разные варианты могут обозначать разных контрагентов или комбинации каналов закупки.
- Составные значения вида «Поставщик A/Поставщик B» вынести на ручную проверку: не превращать их автоматически в поставщика или две привязки.
- Позиции без поставщика импортировать со статусом «Требует привязки»; провизор/шеф не должны терять такие позиции. Их можно включить в заявку, но они отображаются отдельной группой «Без поставщика» до назначения продавца.
- `???`, пустой остаток и другие нечисловые значения хранить как неопределённое значение, не подменяя нулём.
- Не импортировать количества с листов «Терминал су-шефа» и «Заказы поставщикам» как активные заказы. Это шаблон/тестовые значения, не подтверждённая история фактических закупок.
- До импорта показать предварительный просмотр: количество записей, дубликаты, позиции без категории/продавца, неизвестные остатки; позволить скачать отчёт об ошибках.

### 5.2 Сущности приложения

- **Пользователь:** имя, логин, хэш пароля, роль, активность, дата создания.
- **Категория:** название, порядок сортировки, активность.
- **Товар:** название, категория, единица измерения, минимальный остаток (необязателен), активность, примечание.
- **Поставщик:** отображаемое название, исходное название из файла, активность, контакты (необязательны).
- **Привязка товар–поставщик:** товар, поставщик, основной/дополнительный, комментарий/условия (необязательны).
- **Заявка:** номер, автор, дата создания/отправки, статус, комментарий.
- **Позиция заявки:** товар, количество, единица измерения, комментарий, поставщик на момент отправки, статус обработки.

Для надёжной истории сохранять название товара и поставщика на момент отправки как снимок данных, чтобы последующее переименование справочника не меняло старые заявки.

## 6. Статусы

- Заявка: «Черновик» → «Отправлена» → «В работе» → «Выполнена»; при необходимости «Отменена».
- Позиция закупки: «К заказу» → «Заказано» → «Получено»; дополнительный статус «Нужно уточнить».

Изменение статуса сохраняет автора и дату. Финальные статусы не удаляют историю. Правила редактирования/отмены отправленной заявки должны быть ограничены: шеф может отменить её с причиной; сушеф не меняет отправленную заявку, а создаёт новую или просит шефа внести корректировку.

## 7. Технические требования и поставка

- **Frontend:** React, адаптивная вёрстка, работа через REST API.
- **Backend:** FastAPI, валидация входных данных, REST API, документация OpenAPI.
- **База данных:** PostgreSQL; миграции схемы при старте/деплое.
- **Аутентификация:** сессия или подписанный токен в защищённой cookie; пароли хранить только в виде стойкого хэша. Доступ к API проверяет роль.
- **Контейнеризация:** `docker-compose.yml` с сервисами `web`, `api`, `db` и при необходимости обратным прокси. Данные PostgreSQL хранятся в именованном volume.
- **Конфигурация:** `.env.example`, секреты не включаются в образ; переменные для пароля БД, ключа приложения, домена и режима запуска.
- **Первый запуск:** инструкция одной командой для локальной проверки, автоматическое применение миграций и создание начального администратора через переменные окружения или отдельную команду.
- **Эксплуатация:** healthcheck для API и базы, логи ошибок, резервное копирование/восстановление PostgreSQL описаны в README. Не хранить загруженные таблицы внутри контейнера без постоянного тома.
- **Защита:** HTTPS на сервере через reverse proxy, ограничение попыток входа, проверка ролей, безопасная обработка пользовательских строк, резервное копирование.

## 8. Критерии приёмки

1. Шеф может создать аккаунты трёх ролей, отключить аккаунт и изменить справочные данные.
2. Сушеф на телефоне находит товар по названию, выбирает категорию, вводит количество и комментарий, отправляет заявку и видит её статус.
3. Отправленная заявка сохраняет автора, время, позиции и количества; пустые/нулевые количества не отправляются.
4. Провизор видит новые заявки, список позиций группируется по поставщикам, непривязанные товары выделены отдельно, статусы обработки сохраняются.
5. Шеф видит все заявки и изменения статусов.
6. Поиск работает по названию товара; фильтрация — по категории, дате, поставщику и статусу, где это уместно для роли.
7. Импорт сообщает о дубликатах и непривязанных позициях; значения `???` не превращаются в ноль; тестовые количества не создают заказов.
8. Локальный запуск выполняется по README через Docker Compose; после перезапуска контейнеров данные остаются в PostgreSQL volume.
9. Основные экраны пригодны для узкого мобильного экрана и широкого экрана компьютера.

## 9. Решения, которые нужно подтвердить перед реализацией

1. **Единицы:** в книге явно указано «кг» только в заголовке листа заказов поставщикам, но для всего каталога единицы не размечены. Нужно подтвердить, что все товары измеряются в кг, либо предоставить единицу для каждого товара (кг, г, шт., л, уп.).
2. **Поставщики:** разрешено ли одному товару иметь несколько поставщиков и как выбирать поставщика в конкретной заявке? Составные значения через `/` требуют ручной расшифровки.
3. **Остатки:** поле названо «Минимальный остаток», однако в сценарии не указано, кто и где вводит текущий остаток. Первая версия не рассчитывает потребность автоматически без текущего остатка.
4. **Каталог:** подтвердить, что напитки и непродовольственные позиции исключаются из каталога сушефа, как указано в пояснении Excel, и уточнить статус строк, похожих на служебные заголовки.
5. **История:** определить срок хранения заявок и нужно ли провизору закрывать закупку целиком либо достаточно статусов по позициям.
